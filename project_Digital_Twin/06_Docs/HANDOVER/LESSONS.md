# LESSONS — กับดักที่เจอมาแล้ว อย่าเสียเวลาซ้ำ

ไฟล์นี้คือส่วนที่มีค่าที่สุดของเอกสารส่งมอบชุดนี้ รวมปัญหาที่เจอจริงระหว่างทำโปรเจกต์
(ไม่ใช่กฎที่นั่งคิดเอาเอง) พร้อมอาการที่สังเกตได้ สาเหตุจริง และวิธีแก้/วิธีป้องกัน
เพื่อให้คนที่รับช่วงต่อไม่ต้องเดินชนกำแพงเดิมซ้ำ

## หมวดสภาพแวดล้อม / เครื่องมือ

### path ที่มีอักษรไทยทำ `pip install` พัง

**อาการ:** ติดตั้ง `numpy==1.26.4` ด้วย `pip install` แล้วขึ้น
```
UnicodeEncodeError: 'charmap' codec can't encode characters
```

**สาเหตุจริง:** เวอร์ชันนั้นไม่มี wheel สำเร็จรูปสำหรับ Python 3.13 บนเครื่องที่ใช้ pip จึงพยายาม
build จาก source code แล้วไปสะดุดกับ path ที่มีคำว่า `สหกิจ` (โฟลเดอร์โปรเจกต์อยู่ใต้ path ภาษาไทย)

**วิธีแก้:** ใช้เวอร์ชันแพ็กเกจที่มี wheel สำเร็จรูป (`cp313`) และบังคับด้วยแฟลก
`--only-binary=:all:` เพื่อไม่ให้ pip พยายาม build จาก source เลย และตั้งตัวแปรแวดล้อม
`PYTHONUTF8=1` ก่อนรันสคริปต์ที่มีการ print ข้อความภาษาไทย

**ทำไมต้องรู้:** ถ้าเจอ error เข้ารหัสอักขระประหลาดๆ ระหว่าง `pip install` ให้นึกถึง path ภาษาไทย
ไว้ก่อนเป็นอันดับแรก ไม่ใช่ไปหาสาเหตุที่ตัวแพ็กเกจ

### ต้องมี venv แยกต่อโปรเจกต์ ห้ามใช้ Python กลางของเครื่อง

**อาการ:** `run_demo.ps1 check` (preflight check ของโปรเจกต์) ไม่ผ่าน ทั้งที่ไม่เกี่ยวกับโค้ด
ในโปรเจกต์เลย

**สาเหตุจริง:** Python ที่ติดตั้งไว้กลางเครื่อง (ไม่ใช่ของโปรเจกต์) มีแพ็กเกจ `easyocr` ติดตั้งอยู่
แต่ขาด dependency `opencv-python-headless` ทำให้คำสั่ง `pip check` ที่ preflight เรียกใช้ ล้มเหลว
เพราะไปตรวจทั้งเครื่อง ไม่ใช่แค่โปรเจกต์นี้

**วิธีแก้:** สร้าง virtual environment แยกต่อโปรเจกต์เสมอ (สคริปต์ `setup_python.ps1` ทำให้แล้ว)
อย่าเรียกใช้ Python ตัวกลางของเครื่องตรงๆ

### ไม่มี `openpyxl`, ไม่มี `markitdown`, ไม่มี LibreOffice บนเครื่องที่ทำเอกสารชุดนี้

**ผลกระทบ:** อ่านไฟล์ `.xlsx` ด้วยไลบรารีมาตรฐานไม่ได้ และคำนวณสูตร Excel ใหม่ (recalc) ก็ทำไม่ได้

**วิธีแก้ที่ใช้ได้:** ไฟล์ `.xlsx` คือไฟล์ zip ที่มี XML อยู่ข้างใน อ่านเนื้อหาได้ด้วย `zipfile` +
`xml.etree` ของ Python มาตรฐานโดยไม่ต้องติดตั้งแพ็กเกจเพิ่ม แต่วิธีนี้**อ่านค่าที่ cache ไว้ได้
เท่านั้น ไม่สามารถคำนวณสูตรใหม่ให้ได้** — ถ้าแก้สูตรในไฟล์แล้วต้องการยืนยันว่ายอดถูกต้องจริง
**ต้องเปิดด้วย Excel จริงสักครั้ง** (ดูหัวข้อ "ใบสั่งซื้อมียอดต่ำกว่าจริง" ด้านล่าง — ฉบับแก้แล้ว
ยังไม่เคยถูกเปิดยืนยันด้วย Excel จริงเลย)

**หมายเหตุเสริม:** Excel เก็บวันที่เป็นตัวเลขนับจากวันที่ 1899-12-30 เช่น `46216` = 13 ก.ค. 2026
ถ้าต้องอ่านวันที่จาก XML ดิบให้แปลงด้วยสูตรนี้

## หมวดฮาร์ดแวร์ / พอร์ต

### เลขพอร์ต COM เปลี่ยนทุกครั้งที่ถอดเสียบสาย — อย่าจดจำเลขไว้ตายตัว

**อาการที่เคยเกิด:** เอกสารบันทึกไว้ว่าจอ HMI อยู่ที่ COM7 แต่พอเสียบใหม่กลายเป็น COM8
ถ้าใครอ่านเอกสารเก่าแล้วไปแก้โค้ด hardcode พอร์ตตามนั้น จะต่อไม่ติดโดยไม่รู้สาเหตุ

**วิธีที่ถูก:** ตัวเปิดระบบ (launcher) ตรวจพอร์ตจอจาก**ชื่ออุปกรณ์** ที่ Windows รายงาน
(`STMicroelectronics STLink Virtual COM Port`) โดยอัตโนมัติ ไม่ hardcode เลขพอร์ต — เวลาต้อง
ต่อเอง ให้ดูชื่ออุปกรณ์ใน Device Manager แทนการเดาจากเอกสารเก่า

กล้อง OpenMV H7 Plus ยืนยันแล้วว่าใช้ชื่ออุปกรณ์ `USB Serial Device` และปัจจุบันคือ COM6
(เลขนี้ก็เปลี่ยนได้เหมือนกันถ้าถอดเสียบสายอื่นแทรก)

### ห้ามใช้ `taskkill /F /IM python.exe` เด็ดขาด

**เหตุผล:** คำสั่งนี้ฆ่า process Python **ทุกตัวที่รันอยู่บนเครื่อง** ไม่ใช่แค่ของโปรเจกต์นี้
ถ้ามีโปรแกรมอื่นที่ใช้ Python รันอยู่พร้อมกัน จะถูกฆ่าตายไปด้วยโดยไม่ได้ตั้งใจ

**วิธีที่ถูก:** ใช้ `STOP.bat` ของโปรเจกต์ ซึ่งปิดเฉพาะ process/พอร์ตที่โปรเจกต์นี้เปิดไว้จริง และ
ตรวจซ้ำว่าพอร์ต 8000/8765/8766/8767 และพอร์ต COM ที่เกี่ยวข้องว่างจริงหลังปิด ไม่ใช่แค่บอกว่าปิดแล้ว

### ไฟล์ `.bat` ต้องเป็น CRLF, ไฟล์ `.ps1` ต้องเป็น UTF-8 with BOM

**อาการถ้าผิด:** `.bat` ที่เป็น LF ล้วนจะทำให้ `cmd.exe` อ่านบรรทัด `powershell -NoProfile` ผิด
เกิด error `'NoProfile' is not recognized` ส่วน `.ps1` ที่ไม่มี BOM จะถูก PowerShell 5.1 อ่านด้วย
codepage ของระบบแทน UTF-8 ทำให้ข้อความภาษาไทยในสคริปต์เพี้ยนทั้งไฟล์

**วิธีป้องกัน:** ตรวจการเข้ารหัสไฟล์ก่อนบันทึกทุกครั้งที่แก้สคริปต์เปิด/ปิดระบบ

## หมวด git

### `git mv` เข้าโฟลเดอร์ที่อยู่ใน `.gitignore` จะดึงไฟล์กลับเข้า tracking

**อาการ:** ย้ายไฟล์ที่ git ติดตามอยู่แล้วเข้า `_Archive/` (ซึ่งตั้งใจใส่ไว้ใน `.gitignore` เพื่อไม่ให้
เก็บซ้ำ) แต่ `git mv` กลับดึงไฟล์นั้นเข้าสู่การติดตามที่ path ใหม่แทนที่จะปล่อยตาม `.gitignore`
เท่ากับเนื้อหาถูกเก็บซ้ำสองรอบใน git ขัดกับเหตุผลที่ ignore โฟลเดอร์นั้นตั้งแต่แรก

**วิธีแก้:** รัน `git rm --cached` ที่ path ปลายทางตามหลังทุกครั้งที่ `git mv` เข้า `_Archive/`
(ไฟล์บนดิสก์ไม่ถูกแตะ แค่เอาออกจากการติดตามของ git)

### `git reset --hard` ลบงานที่ยังไม่ commit ไปด้วย ไม่ใช่แค่ย้อน commit

**อาการที่เคยเกิด:** ใช้ `git reset --hard` เพื่อย้อน commit ที่มีปัญหาเรื่อง line ending
แต่งานที่แก้ไว้แล้วและยังไม่ได้ commit หายไปพร้อมกัน ต้องทำใหม่

**บทเรียน:** ก่อนใช้คำสั่งที่ลบล้างประวัติ ให้ตรวจสอบก่อนว่ามีงานที่ยังไม่ commit ค้างอยู่หรือไม่

### line ending ปนกันในไฟล์เดียวกัน ทำให้ diff บวมผิดปกติ

**อาการ:** ไฟล์อย่าง `gateway_fsm.py` และ `cad/index1.html` มีทั้งบรรทัดแบบ CRLF และ LF ปนกันอยู่
ในไฟล์เดียว เมื่อใช้เครื่องมือแก้ไฟล์บางตัวที่เขียนทับทั้งไฟล์ (แทนที่จะแก้เฉพาะส่วนที่เปลี่ยน)
จะทำให้ git มองว่าทุกบรรทัดเปลี่ยน — เคยทำให้ diff ของการแก้เล็กๆ บวมจาก 38 บรรทัดเป็น
**564 บรรทัด** ทำให้ประวัติ git อ่านไม่ออกว่าจริงๆ แล้วแก้อะไรไปบ้าง

**วิธีป้องกัน:** ตรวจ `git diff --stat` ก่อน commit เสมอ ถ้าตัวเลขบวมผิดปกติเทียบกับสิ่งที่ตั้งใจแก้
ให้สงสัยเรื่อง line ending ก่อน วิธีแก้คือแก้ไฟล์แบบอ่าน/เขียน binary แล้วคงบรรทัดขึ้นบรรทัดใหม่
(newline) เดิมของบรรทัดที่ใช้อ้างอิงตำแหน่งไว้ ไม่ให้เครื่องมือแปลงทั้งไฟล์เป็นแบบเดียว

### `git commit` ด้วยข้อความหลายบรรทัดในเชลล์ที่ผิดชนิด

**อาการ:** เขียนข้อความ commit หลายบรรทัดด้วยรูปแบบ here-string ของ PowerShell (`@'...'@`)
แต่ไปรันใน Bash ทำให้ตัวอักษร `@` ติดอยู่หัวข้อความ commit

**วิธีแก้:** เขียนข้อความ commit ลงไฟล์ก่อน แล้วใช้ `git commit -F ไฟล์` แทนการพิมพ์ inline
ข้ามปัญหาเรื่องเชลล์ที่ต่างกันตีความ syntax ไม่ตรงกัน

### `.gitignore` กันไฟล์รูปภาพสำคัญออกไปด้วยโดยไม่ตั้งใจ

**อาการ:** กฎ `*.jpg` / `*.png` ที่ใส่ไว้เพื่อกันไฟล์โมเดล 3D กับ build asset ไม่ให้เข้า git
ดันกันรูปถ่ายหน้าจอ HMI ของเครื่องต้นแบบ (หลักฐานการออกแบบที่ถ่ายไว้และหาใหม่ไม่ได้
ถ้าเครื่องถูกตั้งค่าใหม่) ออกไปด้วย

**วิธีแก้:** เพิ่มกฎยกเว้นเฉพาะที่ `!06_Docs/**/*.jpg` และ `!06_Docs/**/*.png` เพื่อให้รูปในโฟลเดอร์
เอกสารยังคงถูก track แม้กฎทั่วไปจะกันรูปประเภทนี้ไว้

**บทเรียนทั่วไป:** เขียน `.gitignore` แบบกว้างสำหรับไฟล์ build/asset ให้ระวังเสมอว่ามันอาจกวาด
ไฟล์สำคัญที่บังเอิญนามสกุลเดียวกันไปด้วย ต้องเช็คว่ามีข้อยกเว้นที่จำเป็นครบหรือยัง

## หมวดการวินิจฉัยปัญหา — บทเรียนที่ทำให้เสียเวลาซ้ำ

### อย่าสรุปจากชื่อโฟลเดอร์/ไฟล์ ต้องเปิดดูเนื้อหาข้างในก่อนเสมอ

เคยสำรวจโฟลเดอร์แล้วสรุปว่าโฟลเดอร์หนึ่งคือ firmware ของ STM32H7S ที่ตั้งชื่อผิดเป็นชื่อเว็บแอป
พอเปิดค้นจริงในไฟล์โปรเจกต์ (`.ioc`, EWARM, MDK-ARM, CubeIDE, linker script) กลับ**ไม่เจอไฟล์
firmware เลยสักไฟล์** ข้างในมีแต่สำเนาเว็บแอปกับโฟลเดอร์ config เท่านั้น ของจริงอยู่ในอีกโฟลเดอร์
หนึ่งที่ชื่อไม่บอกใบ้เลยว่าเป็น firmware (`NOXCORE/`)

### อย่าสรุปว่าไฟล์ประเภทเดียวกันมีโครงสร้างเหมือนกันทุกไฟล์

ตอนตรวจใบสั่งซื้อ (ดูหัวข้อถัดไป) เคยสรุปผิดว่าไฟล์ `BOM-Sealing.xlsx` ไม่มีสูตร SUM เลยและยอด
ถูกพิมพ์มือ — สาเหตุที่สรุปผิดคือไปดูคอลัมน์ H ตามที่ไฟล์อื่นๆ ในชุดเดียวกันใช้ ทั้งที่ไฟล์นี้
วางราคาไว้คอลัมน์ **G** ต่างหาก (คอลัมน์ H เป็นลิงก์สั่งซื้อ) ทำให้มองไม่เห็นสูตรที่มีอยู่จริง
**อย่าเหมาว่าไฟล์ประเภทเดียวกันในชุดเดียวกันจะวางเลย์เอาต์เหมือนกันหมด**

### ขอบเขตที่สำรวจ คือขอบเขตที่สรุปได้เท่านั้น

ตอนเทียบสำเนาโปรเจกต์ที่กระจัดกระจาย 5 ชุดด้วย SHA-256 แล้วสรุปว่า "ชุดล่าสุดเป็น superset
ของทุกชุด ไม่มีไฟล์ไหนหายแน่นอน" — ข้อสรุปนั้นถูกจริง แต่ถูก**เฉพาะภายในขอบเขตที่สำรวจ**เท่านั้น
ภายหลังพบว่ามีสำเนาที่ 6 อยู่นอกขอบเขตที่สำรวจไปแต่แรก (คนละโฟลเดอร์แม่เลย) และเป็นตัวที่ใช้งาน
จริงมาตลอด ต้องนำมาเทียบเพิ่มทีหลัง

### อ่าน protocol จริงก่อนสรุปว่าโค้ดพัง

เคยเขียนเทสต์ส่งคำสั่งเปลี่ยนโหมดด้วย `{"action":"MODE","value":"semi"}` แต่โค้ดฝั่งรับอ่านคีย์
ชื่อ `"mode"` ไม่ใช่ `"action"` ทำให้ระบบไม่เคยสลับโหมดจริง และดูเหมือนฟีเจอร์ Semi-Auto พัง
ทั้งที่จริงๆ โค้ดทำงานถูกอยู่แล้ว แค่เทสต์ส่งผิด protocol — ก่อนสรุปว่าโค้ดมีบั๊ก ให้ตรวจสอบก่อนว่า
สิ่งที่ส่งไปตรงกับ protocol ที่โค้ดฝั่งรับคาดหวังจริงหรือไม่

### อย่าหยิบตัวเลขผลทดลอง sealing จากสไลด์ EP1 ไปใช้กับเครื่องใหม่

สไลด์ `Packing-EP1` (Canva `DAHI4VEM_QI`) หน้า 25–27 มีตัวเลขผลทดลอง sealing เหล็ก vs สแตนเลส
ที่เคยหาไม่เจอในเอกสารมานาน (ดู WORKLOG (repo พัฒนาของนักศึกษา) หัวข้อ 2026-08-07) แต่ตัวเลขชุดนั้น
**วัดจากวัสดุคนละแบบกับเครื่องที่กำลังสร้างใหม่ในโปรเจกต์นี้** เอาไปใช้เป็นค่าตั้งต้นหรือเกณฑ์ตัดสิน
ของเครื่องใหม่ตรงๆ ไม่ได้ ต้องทดลองซ้ำกับวัสดุ/โครงสร้างจริงของเครื่องใหม่ก่อนเสมอ
รายละเอียดตัวเลขทั้งหมดพร้อมคำเตือนเต็ม ดู SEALING_TEST_RECORD (repo พัฒนาของนักศึกษา)

นี่คือกรณีศึกษาที่สำคัญที่สุดในโปรเจกต์นี้ เพราะเป็นตัวอย่างของการสรุปสาเหตุเร็วเกินไปจาก
หลักฐานที่ยังไม่พอ แล้วต้องย้อนกลับมาแก้ไขในภายหลัง

**สิ่งที่เกิดขึ้น:** ตอนทดสอบเครื่องกับฮาร์ดแวร์จริง สังเกตว่าทุกครั้งที่กด Reset บนจอ HMI แล้ว
ระบบจะเข้าสถานะ `ALARM` (ที่ตอนนั้นเข้าใจว่าคือ ESTOP) ภายใน 1 วินาที ระบบค้างที่ `LOAD_CARRIER`
ทันที เทียบกับตอนรันโหมด `START_WEB.bat` (ไม่ต่อฮาร์ดแวร์เลย) ที่ระบบเดินได้ครบ 8 สถานะไม่มี
อาการนี้เกิดขึ้นเลย

จากการเทียบสองโหมดนี้ ตอนนั้นสรุปว่า **"แยกได้แล้วว่าปัญหาอยู่ฝั่งฮาร์ดแวร์ ไม่ใช่โค้ด"** และ
บันทึกข้อสรุปนี้ลง WORKLOG ไปแล้ว

**สิ่งที่ทำให้ต้องกลับมาทบทวน:** ภายหลังไล่ตรวจโค้ดทั้ง 3 ชั้นของระบบอย่างละเอียด (Rust bridge
ที่คุยกับบอร์ด Modbus, เฟิร์มแวร์ TouchGFX ของจอ HMI, และตัวรับคำสั่งฝั่ง Python) พบว่า:

- Rust bridge ที่คุยกับบอร์ด I/O **ไม่มีคำว่า estop หรือ emergency หรือ interlock อยู่ในโค้ดเลย
  แม้แต่คำเดียว** — ไม่มี input ตัวไหนถูกแมปให้เป็น ESTOP ทั้งสิ้น
- เฟิร์มแวร์ TouchGFX ของจอ HMI **ส่งคำสั่งออกมาได้แค่ 5 แบบ**: `START`, `STOP`, `RESET`,
  `SET_PARAMS`, `DECISION` — ไม่มีการส่งคำสั่ง ESTOP ออกมาเลยไม่ว่ากรณีใด
- ตัวรับคำสั่งฝั่ง Python ใช้ `json.loads` แบบเข้มงวด บรรทัดไหนที่ไม่ใช่ JSON ที่ถูกต้องจะถูก
  ข้ามไปเงียบๆ ไม่ทำอะไร — แปลว่าสัญญาณรบกวน (noise) บนสายสื่อสารก็กลายเป็นคำสั่ง ESTOP ไม่ได้
  ด้วยเช่นกัน

สรุปคือ**ไม่มีทางใดเลยที่ฮาร์ดแวร์จะส่งคำสั่ง ESTOP เข้ามาได้จริง** เพราะไม่มีโค้ดจุดไหนรองรับ
การส่งคำสั่งนี้จากฮาร์ดแวร์เลย ทางเข้าเดียวที่มีอยู่จริงในระบบคือปุ่ม ESTOP จำลองบนหน้าเว็บเท่านั้น
และเจ้าของโปรเจกต์เองก็ยืนยันว่าเครื่องยังไม่มีปุ่ม ESTOP ฮาร์ดแวร์จริงติดตั้งอยู่เลย

**ต้องมองหาคำอธิบายอื่น:** ระบบมี `ALARM` ที่เข้าได้ 6 ทาง ไม่ใช่แค่ทาง ESTOP ทางเดียว และ 4 ใน
6 ทางเป็น**ตัวสุ่มที่ทำงานอยู่ตลอดเวลา**ไม่ว่าจะต่อฮาร์ดแวร์จริงหรือไม่ (ดูตารางเต็มใน
`STATUS.md`) ที่น่าสงสัยที่สุดคือ `CHECK_TEMP` ซึ่งมีโอกาสสุ่มหลุดช่วงที่ยอมรับได้ถึง ~13% ต่อรอบ
และ`CHECK_TEMP`อยู่ที่ลำดับ 9 จาก 17 สถานะทั้งหมด — เดินไม่กี่วินาทีก็ถึงพอดี ตรงกับอาการ "เด้ง
ภายใน 1 วินาที" ที่เคยสังเกตเห็น

**บทเรียนที่ได้:**

1. **การเทียบสองสภาพแวดล้อม (ต่อฮาร์ดแวร์ / ไม่ต่อฮาร์ดแวร์) พิสูจน์ได้แค่ว่า "อาการเกี่ยวข้องกับ
   ฮาร์ดแวร์" ไม่ได้พิสูจน์ว่า "อาการคือ ESTOP"** — ทั้งสองเรื่องเป็นคนละคำถามกัน แต่ตอนนั้น
   ปนกันไปโดยไม่ได้ตั้งใจ
2. **ต้องดูข้อความ alarm จริงที่ขึ้นตอนเกิดเหตุก่อนสรุปสาเหตุเสมอ** อย่าตั้งชื่อปรากฏการณ์จาก
   ความรู้สึกแรกเห็น (ในที่นี้คือ "มันดูเหมือนกด ESTOP") ต้องอ่านข้อความจริงที่ระบบพิมพ์ออกมา
3. **วิธีปิดคดีนี้อย่างเด็ดขาด:** ครั้งต่อไปที่อาการนี้เกิดขึ้น ให้จดข้อความ alarm ที่ขึ้นจริงบน
   จอ/เว็บทันที ถ้าข้อความนั้น**ไม่ใช่** `EMERGENCY STOP PRESSED` เป๊ะๆ ตัวต่อตัว แปลว่า**ไม่ใช่
   บั๊ก ESTOP** และข้อสรุปเดิมที่เคยบันทึกไว้ว่า "แยกได้แล้วว่าปัญหาอยู่ฝั่งฮาร์ดแวร์" ต้องถูกถอน
   อย่างเป็นทางการ — งานนี้ยังไม่ได้ทำ เพราะครั้งถัดไปที่ทดสอบฮาร์ดแวร์แล้วเกิดอาการนี้ ยังไม่มี
   ใครจดข้อความไว้ทัน
